# Plan: real design styles and a much wider furniture library

Goal (from the brief): a person asks for "an industrial bookcase", "a mid-century sideboard", "a Scandinavian nightstand" or "a rustic farmhouse kitchen" and gets a piece that clearly reads as that style in the 3D view, in `render_look` and in the PDF, while staying buildable, priced and valid. The app keeps owning construction; the model keeps making design decisions (see `redesign-report.md`).

This plan splits the work into five phases. Each phase is its own branch and PR to `dev`, with screenshots, `npm test`, `npm run lint` and `npx tsc --noEmit` green. The PRs are stacked in order: each branch starts from the previous one, and every PR targets `dev`, so merging them in order keeps each diff small.

## Guiding decisions

1. **Styles write explicit attributes; saved designs never read the style table.** A style is a recipe that sets materials, legs, handles, fronts, tops and details on the modules. The generator only reads what is stored in the module. Changing a style definition later never changes an old project, its history or its quote. The composition keeps `style` only as a label (UI, agent context, defaults for pieces added later).
2. **One mechanism per concept, used by every furniture type.** Legs and bases, handles, front faces, tops and frames are generic module attributes (`module.look`), generated by the same code for a rack, a wardrobe, a kitchen row or a table. Recipes never draw a leg or a handle themselves.
3. **Cut parts and fittings are different things.** Pieces that a shop cuts or orders to size stay in `generateComposition().parts` (sheets, solid wood slabs, stone, glass, cane inserts, plinths, cornices) and go to the parts list, the collision check and the bounds. Things that are bought or welded (legs, casters, handles, steel frames, LED strips, hooks) come from `fittingsOf(d)`, priced per unit or per metre, drawn in every view, but never in the cut plan.
4. **Materials have a category.** `sheet`, `solid`, `metal`, `glass`, `stone` and `fiber` (cane). Each part role accepts some categories (a carcass is sheet, a leg is wood or metal, a top can be sheet, solid, stone, glass or metal). Validation says which in a sentence the model can act on. Pricing uses the category's unit: sheets by the cut plan, solid wood by m³, stone, glass and cane by m², steel tube by metre.
5. **Old projects load unchanged.** Schema v4 only adds optional fields. A v3 (or v2) revision migrates on read to the same geometry, the same parts and the same quote; a test pins this on real saved compositions.
6. **Small agent surface.** New capabilities reach the model as: a `style` field on `asset.add`, one `style.apply` operation, a `look` patch on `module.edit`, two front types, and new asset ids. `place` and `row_build` inherit the project style on their own, so the model does not repeat it. The asset catalog is rewritten in a denser line so 29 assets still fit the 6000 character budget.

## Data model (schema v4)

```ts
Composition { schemaVersion: 4; style?: StyleId; modules; connections }
Module {
  ...v3 fields (feet stays the height that lifts the box),
  kind?: 'panel' | 'ledge' | 'table',
  look?: {
    legs?: LegType; legMaterialId?: MaterialId;          // base type; feet = its height on boxes
    handle?: HandleType; handleMaterialId?: MaterialId;  // default 'bar' (today's look)
    front?: FrontStyle; insertMaterialId?: MaterialId;   // flat, shaker, slatted, glass, mesh, cane
    top?: { materialId; thickness; overhang; edge };     // overhanging top, merged along a row
    cornice?: boolean; frame?: boolean; frameMaterialId?: MaterialId;
    backMaterialId?: MaterialId; led?: boolean;
  };
  shelves?: number; drawers?: number;                    // table kind only (phase 4)
}
Front { type: 'single' | 'double' | 'drawers' | 'sliding' | 'flap'; style?: FrontStyle; handle?: HandleType; ... }
```

- `LegType`: palito (today's default), tapered, splayed, block, turned, bun, hairpin, tube, pipe, sled, frame (steel stand), trestle, plinth (recessed kick), skirt (visible base), casters, wall (wall-hung table). Each has a height range, the module kinds it fits and the material categories it takes.
- `HandleType`: bar, knob, cup, edge, groove (J-pull), cutout, strap, none (push to open).
- `EdgeProfile`: square, rounded, chamfer.

## Phase 1. Materials, part kinds and fittings (engine, schema, pricing)

Branch `feat/estilos-1-materiais`.

- Material catalog with categories and 20 new materials: pine, ash and smoked oak sheets; oak, walnut, freijó, pine, ash and smoked oak solid wood; black steel, brushed steel, brass, bronze; clear, smoked and ribbed glass; white marble, Nero marble, travertine; cane. Existing ids and prices unchanged.
- Schema v4 with migration, `Composition.style`, `Module.look`, front `style`/`handle` overrides. zod plus `superRefine` for every rule: material category per role, leg height per type, top thickness per category, overhang, cornice only on boxes without a top, contrasting back only with a back, glass, mesh and cane only on doors.
- Generation: overhanging tops merged along side-by-side rows (overhang trimmed where a neighbour blocks, runs meet at the middle of a shared panel), plinth and skirt boards, cornices along rows, contrasting backs, framed fronts with an insert part (glass, mesh, cane) that opens with the door. Parts carry `materialId`, `category`, a `face` (shaker, slatted, frame, edge profile) and the front's `handle`.
- `lib/fittings.ts`: legs of every type (positions, splay, sizes), casters, steel stands and outlines, LED strips and handles, each with geometry and a bill of materials. `drawingParts` moves here and draws them; the 3D view and the PDF photo render the legs, stands, outlines and LED with their real shapes (`lib/scene-fittings.ts`).
- Cut plan takes only sheet parts. Quote: new "Materiais" section (solid m³, stone, glass and cane m², stone edge finishing, steel tube by metre and welding), hardware per type (legs, casters, levelers, handles, push latches, LED), front machining. `mergePrices` keeps old saved tables working. v3 feet without a chosen type stay unpriced, as before.
- UI: finish pickers filtered by category, price table grouped by category plus hardware, part kinds in the parts list; glass, metal and stone parts get a matching surface in the 3D view (transparency, metalness).
- Tests: a golden snapshot of the v3 engine (bench scenes, every asset at its size limits, the demos) proves migrated projects keep the same parts, drawing, quote and cut plan; validation limits; part generation per feature; quote per category; ops (look patch, base shared along a row, front overrides).

## Phase 2. Shapes: handles, fronts, tops and motion in every view

- Editor: a "Estilo e acabamento" block in the module panel (legs, handle, front style, top, cornice, frame, back, LED), plus sliding and flap in the front picker.
- Screenshots: each leg type, each handle type, each front style, sliding and flap open and closed, `render_look` image, PDF page.

## Phase 3. The style layer

Branch `feat/estilos-3-estilos`.

- `lib/styles.ts`: industrial, mid-century, Scandinavian, minimalist, rustic, classic and Japandi. Each bundles a palette (body, fronts, tops, accents), bases for low, tall and table pieces, handle and finish, front style, top and edge, details (cornice, frame, contrasting back, LED), proportions (for example mid-century low and long, Japandi low) and the recipes it suits, with keywords in Portuguese ("anos 60", "loft", "nórdico", "fazenda", "provençal", "ripado").
- `applyStyle(d, style, ids?)`: one pure function used everywhere. Rules by role (low floor piece, tall piece, wall-hung, wall panel, shelf, table), envelope preserved when restyling (a top or a different base does not change the piece's overall size), materials from the palette unless the person chose them.
- `style.apply` operation in the contract (restyle the whole project or one piece), with its change card and undo like any edit. `asset.add` takes `style`; recipes receive the style and adapt (proportions, open niches for airy styles, sliding doors for minimalist wardrobes, glass or mesh doors for industrial).
- UI: style chips in the template gallery (the thumbnails redraw in the chosen style) and a "Estilo" row in the project panel that restyles the selected piece or the whole project, with a preview before applying.
- Tests: every asset × every compatible style across its size range (`tests/assets.test.ts`); restyle keeps the envelope; styles are distinct (a fingerprint of legs, handles, fronts, materials differs pairwise).
- Screenshots: at least three furniture types in all seven styles; gallery with style chips; restyle before and after.

## Risks and how they are contained

- **Part and prompt budgets.** Faces and slats are one part each (the face is geometry, not extra cut parts), so the 200 part limit holds; the catalog line is shortened and tested.
- **Collision and bounds.** Tops, cornices and plinths are real parts, so the existing part collision catches an overhang that hits a neighbour; the generator trims overhang into occupied space before that happens. Legs stay inside the module footprint by construction.
- **Rendering cost.** Custom geometry is cached by shape and size; parts without a face keep today's unit box.
- **Compatibility.** Every consumer of `materials`, `feetOf`, `schemaVersion` and part kinds is updated in phase 1, with the migration test on real saved projects.
